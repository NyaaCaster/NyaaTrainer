# 方法 E：内存扫描 + 锁定（兜底法与锁定工程学）

> **本文解决什么**：引擎**没有**任何可编程通道（无脚本 eval、无框架 API、数据文件封闭）时的
> 唯一修改手段——扫描内存找当前值；以及"锁定"（数值不被游戏改回）的**稳定实现学**：
> 什么引擎该把锁挂在哪一层。

## 0. 什么时候才轮到内存扫描

**有脚本通道绝不用扫描**（对比数据来自被剖析的通用修改器的能力面）：

| 引擎 | 有 eval/对象通道吗 | 扫描的角色 |
|---|---|---|
| MV/MZ、RGSS、Ren'Py、Tyrano、krkr、AGTK、SRPG Studio | ✅ 有 | **几乎不用**（偶用作锁定挂点补充） |
| Godot | ✅（脚本文件执行） | 原生层数值可补扫 |
| Wolf | ❌（原生） | 兜底（cheat 功能有稳定性警告——内存不足时禁用） |
| **RM2k/2k3** | ❌（无脚本；兼容运行时给变量表 API） | **锁定主力**（锁条目持久化 `rm2kVarLock.json`） |
| 原生 C/C++ 自研 | ❌ | **唯一通道** |

> Wolf 的教训值得记住：原生引擎的运行时 cheat（hook 数据层改内存 DB 副本）是**官方自己都标注
> "可能导致游戏不稳"的功能**——扫描/内存改写在原生引擎上天然脆弱，能走文件（方法 B）就走文件。

## 1. 扫描方法论（要点回顾，代码见 02 篇 §3）

1. **两次筛选法**：初扫多假设表示（float/dword/百分比/×10）→ 让值变化 → `soChanged` 复筛 →
   值收敛 → 写入测试。**绝不用"值看起来像什么"猜特征**（0~1 浮点撞上颜色分量的血泪案例）。
2. **副本一致性判据**：真值的多份副本应**完全一致**；不一致的（UI 近似值、渲染插值）全排除。
3. **内存类型限制**：排除 `MEM_IMAGE`，视情况含 `MEM_MAPPED`（漏指针的坑见 02 篇 §11）。
4. **扫描前的引擎判定仍然要做**：即便走扫描，知道了引擎类型（Mono/Ruby/Python/V8）也能
   直接用"该引擎的对象布局"解释扫描结果——比如 Ruby 的 `Fixnum` 带低位 tag、Python 的
   `PyLong` 是指针对，扫描出来的"值"未必是裸 int。

## 2. 锁定（freeze）的三层实现——**挂得越高越稳**

"锁定"是修改器的核心功能，也是**最容易做错的功能**。样本工具在三个不同引擎上用了
**三层不同的锁实现**，归纳出一条铁律：

> **锁的挂点应该尽量靠近"引擎写这个值的入口"——挂点越接近数据，锁越稳、越省、越不易穿。**

### 2.1 第一层：hook 引擎的写入口（首选，脚本架构引擎）

**原理**：引擎改变量必须经过自己的 setter。把 setter 挂钩，写入时先查锁表：

```
原 setter(变量, 新值):
    if 锁表里(变量):     → 强制写锁值(或吞掉写入)
    else:                → 正常写
```

- **MV/MZ（V8）**：hook `Game_Variables` / `Game_Switches` 的 `setValue`（样本工具有
  `hookKeysFunc` 模板对 `$dataSystem`/`Game_Variables_setValue`/`Game_Variables` 做
  原型替换注入）；
- **Ren'Py（Python）**：游戏内注册的锁函数集 `lock_set(...)`（登记锁条目）+
  `lock_tick()`（**接管的主循环每 tick 重申锁值**）——Python 对象树没法逐 setter 挂钩
  （属性赋值没有统一入口），所以退到"每 tick 重写"，但**连续失败自动停摆**
  （"lock ticking stopped after repeated failures"——防错误锁把游戏拖死，也防日志刷屏）；
- **RM2k（兼容运行时）**：锁条目持久化在 `rm2kVarLock.json` / `rm2kSwLock.json` /
  `strVarLock.json`（数值/开关/字符串三类锁分文件），由兼容运行时的变量表 API 在
  **游戏读取变量时**返回锁值——等价于"挂在读入口"，比周期写更稳。

### 2.2 第二层：CPU 硬件断点锁（CE 的 freeze 实现）

CE 地址列表的锁定 = 周期重写（默认 400ms 左右）或 `nop` 掉写指令（Auto Assembler）。
优缺点见 `02-stable-address.md`——注意 **nop 写指令对"多来源写同一地址"的游戏会误伤**。

### 2.3 第三层：周期重写（最后手段）

软件定时器反复写值。**必须限流**（不能每帧写，写频繁了游戏卡/存档竞争）+ **失败要留痕**
（`pcall` 吞返回值会让故障变成"日志一片空白"，02 篇硬规矩 19）。

### 2.4 锁定工程学细则（跨引擎通用，样本工具实证）

| 细则 | 原理 |
|---|---|
| **锁条目要持久化** | 重启后锁要能恢复（`*.lock.json` 按引擎分文件：数值/开关/字符串变量锁分开） |
| **锁值显示读真值** | 面板显示"当前实际值"而不是锁目标值——真值≠目标时标红，锁失效立刻可见（02 篇硬规矩 18） |
| **类型感知** | 字符串变量锁与数值锁是**不同机制**（字符串不能周期写整型），分开存储分开渲染 |
| **数组/对象锁要按元素** | 数组变量的锁按索引逐个（`arrayVarLock` 形态），不能锁整个容器引用 |
| **锁失败要停摆** | tick 连续失败 → 停止 tick 并提示，防错误配置拖死游戏 |
| **一个数值一个锁入口** | UI 上每行的锁按钮**只负责那一行**；不做"全部锁定"类批量入口（02 篇硬规矩 16 的教训） |

## 3. 环境排障：本地环回被拦截（通用修改器的头号环境坑）

所有引擎的修改功能都依赖**工具 ↔ 游戏进程的本机环回连接**（回连 WebSocket 或进程内服务）。
被剖析的样本工具对此有**成体系的检测与话术**，归纳成排障流程：

| 现象 | 判据 | 处置 |
|---|---|---|
| 端口被占 | 固定端口段监听失败（报 "TCP port busy"） | 换端口/找出占用进程 |
| 游戏连不上工具 | "no game peer connected"；工具侧专用连接探针 exe 报告连接失败 | 查防火墙对 **127.0.0.1** 的拦截 |
| 连通但极慢 | **RPC 中位延迟**实测远超 0.5ms 基线（工具会测并弹警告） | **本地流量被过滤软件接管**（AdGuard/杀软流量过滤/强制代理）——加白名单**通常没用**（驱动级接管全部本地流量），必须关掉该软件的流量过滤功能或整个退出，重启游戏与工具 |
| 防火墙弹窗没处理 | 游戏首启连不上 | 允许游戏访问本地网络 |

> **为什么加白名单没用**：流量过滤软件在 **Winsock LSP / WFP 驱动层**接管所有本机连接，
> 不是按进程过滤的——环回包照样被绕道代理，延迟到 ms 级，游戏内实时功能（逐句翻译、
> 实时修改）会明显卡顿。这是"修改器装好后明明都配对了却不工作"最常见的根因，
> 而且**症状会被误判成"引擎不支持"**——先测环回延迟再下结论。

## 4. 操作骨架（兜底路径）

```
① 判引擎(总览 §3) → 确认真的没有 A/B/D/F 可用
② 扫描: 两次筛选法(02 篇 §3) → 收敛候选
③ 写入测试: 改一个明显值 → 界面验证 → 用户确认
④ 选锁挂点: 有引擎写入口就 hook(§2.1) → 否则周期重写(限流+停摆)
⑤ 固化: 稳定条目(02 篇) → 重启验证 → 打包(03 篇)
```

## 5. 坑位表（本篇新增；扫描通用坑见 02 篇 §11）

| 坑 | 现象 | 正解 |
|---|---|---|
| 在有 eval 通道的引擎上硬扫内存 | 事倍功半、地址漂移 | 先判引擎再选方法；扫描只是兜底 |
| 原生引擎(RM2k/Wolf)的扫描值当稳定地址 | 重启失效 | 兼容运行时的变量表 API / 文件解析才是稳定来源 |
| 锁挂"周期重写"不挂写入口 | 锁被游戏高频写穿/卡顿 | 优先 hook setter；Ren'Py 式 tick 锁必须限流+停摆 |
| 锁条目不持久化 | 重启锁全丢 | 锁配置落盘（按类型分文件） |
| 面板显示锁目标值 | 锁失效看不出来 | 显示真值，不一致标红 |
| 误判"引擎不支持" | 实际是环回被过滤软件接管 | 测 RPC 延迟基线（<0.5ms 正常）；关流量过滤再试 |
| 字符串变量用数值锁 | 写坏数据/崩溃 | 按类型分锁（数值/开关/字符串三套） |

## 6. 与其它方法的关系

- **E 是兜底**：A/B/D/F 全部失效才轮到 E——但 E 的**锁定**部分（§2）对任何引擎都值得看
  （脚本引擎的锁也该挂 setter 而不是周期写）。
- **E ↔ 02 篇**：02 篇解决"找到的地址怎么固化"；本文解决"锁怎么挂才稳 + 环境为什么连不上"。
