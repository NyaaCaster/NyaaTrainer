# 方法 B：引擎数据文件与存档解析重写

> **本文解决什么**：引擎**没有脚本 eval 通道**（原生 C++ 引擎），或者要改的本来就是
> **数据库定义/存档进度**而非运行时值——此时按**引擎官方数据格式**直接解析、修改、重写文件。
>
> **上位总览**：`05-engine-mod-methods-overview.md`。
> **实证**：Wolf RPG Editor 的 `Game.dat` 解析 + 数据库编辑器 + 工具专用存档路径，是最完整的实现样本。
> 建立：2026-10-02。

---

## 0. 原理

每个引擎的数据文件都有**稳定的容器格式**（魔数、节表、类型标签）。规则引擎式的游戏
（Wolf、RM2k）把**变量/开关/数据库**全部存在数据文件里，游戏运行时只是"读文件→建内存结构"。
因此：

```
文件格式稳定 ⟹ 离线解析 ⟹ 按结构改写 ⟹ 游戏加载时自然生效
```

这是**不碰进程内存**的修改法：**离线、可回滚、能改引擎不给改的东西**（如"数据库里根本没有的物品"
可以新增条目；存档里"没记录的变量"可以补写）。

**两大目标物**：

| 目标物 | 内容 | 修改语义 |
|---|---|---|
| **游戏数据文件** | 数据库（物品/角色/技能/事件指令）、系统配置、变量**定义** | 改"定义"——影响所有新游戏与读档后的行为 |
| **存档文件** | 当前 HP/位置/背包、变量**当前值**、已触发开关 | 改"进度"——直接改变玩家当前状态 |

## 1. 样本一：Wolf RPG Editor（本方法最完整实现）

Wolf 是原生 C++ 引擎，无脚本 eval；它的**所有变量都活在数据库文件里**，所以文件解析是主力方法。

### 1.1 数据容器

| 文件/目录 | 内容 |
|---|---|
| `Data/BasicData/Game.dat` | **三大数据库容器**：系统库（SYS）、用户库（User）、设定库（Conf）——公共事件、可变 DB、字符串变量、数值变量全部在内 |
| `Data/BasicData/SysDataBase` 等子库 | 分库数据（按 `BasicData/SysDataBase` 系路径定位） |
| `Save/` 目录 | 存档（修改器侧生成专用存档目录，见 §1.4） |

### 1.2 解析要点（Game.dat 内部结构）

- **数据库三分类**（工具内部的命名，体现格式语义）：
  `wolfDBName_SYS`（系统数据库）/ `wolfDBName_User`（用户数据库）/ `wolfDBName_Conf`（公共设定）；
- **类型标签体系**：字符串变量与数值变量是**不同类型区**（工具里分 `genVarsJson` / `genStringVarsJson`
  两条解析路径）；
- **编码**：老 Wolf 数据库文本是 **Shift_JIS**——解析时要带码页转换（工具里 `genTypeDefJsonFromShiftJIS` /
  `genItemsJsonFromShiftJIS` 的命名直接暴露了这一点）；WolfRPG 有专门的 `wolfRPGCodePage`/`UTF8` 开关。
- **版本分桶**：Wolf 2.x 与 3.x 格式不同（`wolf225+`/`wolf300+`/`wolf3132+`/`wolf3322+`/`wolf350+`/`wolf3611+`/
  `wolf3695+` 等版本桶），PE 版本资源读出 `WOLF RPG Editor` 版本号后按桶选解析器。

### 1.3 修改形态：三件套

1. **数据库列表（读取）**：解析 `Game.dat` 生成"变量表"（id → 名称/当前值/类型），
   作为修改面板的数据源——**这就是 C 方法（对象映射）在无运行时引擎上的等价物**；
2. **数据编辑器（写回）**：通用 JSON 编辑器组件（数据库编辑模板 `wolfDataMod` /
   `mvDataEditor.html` 同一个组件）编辑任意字段 → 按 Wolf 格式**写回** `Game.dat`；
3. **运行时 cheat（可选）**：hook DLL 侧（`wolfHook.dll`/`wolfHook3.dll`）驻留命令：
   `getFileData` / `getFileDataBin`（引擎数据读）、`setCheatData`（写入）、`wolfVer`（版本）。
   运行时修改 = hook 住引擎的数据访问层，改它的内存 DB 副本。
   ⚠️ 官方提示 Wolf 3.0 的 cheat 未完成、cheat 可能引发游戏不稳（内存不够时还会拒绝启用）。

### 1.4 存档格式坑（Wolf 特有，值得记住的"工具与原版兼容"问题）

- 工具运行时创建的存档，其**格式版本与原版 exe 预期可能不一致**——原版 exe 直接启动会异常。
- 处置：修改器侧存档写进**独立专用目录**，并在"删除修改器数据"流程里**连带清掉修改器格式的存档**；
  用户想回原版玩时先删这些存档。
- 通用教训：**任何"工具写存档"的方法都必须考虑原版引擎的读取兼容性**——存档里往往带
  版本号/结构校验，改写时要同步维护。

### 1.5 运行时修改 Wolf 的第二手段：事件指令

Wolf 的事件指令（`wolf_command` / `wolf_at_digit` / `wolf_A_plus` 等 token 定义）也可以被工具
**离线重写**（事件脚本在数据库内）——"给某事件插一条'变量 A += N'"属于方法 B 与方法 F 的交界。

## 2. 样本二：RPG Maker 系的文件级修改

### 2.1 MV/MZ（JSON 数据库 + rpgsave 存档）

- **数据库是明文 JSON**：`data/Items.json`、`data/Actors.json`、`data/MapInfos.json`、
  `data/CommonEvents.json`、`data/ExternMessage.csv`（外字表）等——**离线编辑 + 引擎加载即生效**。
- 通用修改器的实现走 **VFS 叠加**：把游戏目录挂载成虚拟文件系统（`data/compressed`/`data/encryptData`
  处理加密包），编辑器改的是 VFS 视图，**写回（writeback）时落盘原文件**；多端写入冲突有
  冲突列表（WriteBack Conflicts）与磁盘水位监控——这是"编辑器 + 原文件"模式的工程化形态。
- **存档**：MV/MZ 的 `.rpgsave` 是 **JSON（可被 pako 解压）**——变量/开关/背包都在里面，
  可离线编辑；工具侧把玩家存档整目录 zip 备份（`gameSaveBackup` 机制）后即可安全修改。

### 2.2 XP/VX/VX Ace（Ruby marshal 数据库 + 自定义存档）

- 数据库 `Data/Actors.rxdata`（XP）/`.rvdata`（VX）/`.rvdata2`（VXAce）是 **Ruby Marshal 格式**，
  对象含 `RPG::Actor` 等 marshal 类——解析需要对应 Ruby 版本（1.8.7/1.9.3）。
- 存档 `Save*.rxdata` 等同为 Marshal；**变量/开关/背包**在 `$game_party`/`$game_switches` 的
  序列化对象里。
- ⚠️ 该引擎的 cheat 面板在样本工具里标记为"已弃用等待重写"——**RGSS 系修改优先走方法 A
  （Ruby eval）**，文件法只在"游戏未运行"时用于改数据库。

### 2.3 RM2k/2k3（`RPG_RT.ldb`）

- 数据库/地图树 `RPG_RT.ldb`/`RPG_RT.lmt` 格式封闭（无官方文档），变量定义在其中。
- 样本工具对 RM2k 的策略：**变量/开关的锁定走内存**（`rm2kVarLock.json` 持久化锁条目 + 兼容运行时
  变量表 API），事件指令走方法 F。文件级解析只用于"取变量定义列表"。

## 3. 样本三：Ren'Py / Tyrano / krkr 的存档

| 引擎 | 存档形态 | 修改要点 |
|---|---|---|
| Ren'Py | `saves/` 下 slot 文件（pickle，含 store 变量快照）+ `persistent`（跨档常驻数据） | persistent 与 store 变量**优先走方法 A 运行时改**；离线改档需要对应 Python 版本 pickle |
| TyranoScript | 存档 JSON（`sf`/`f` 变量快照） | JSON 明文，可离线编辑；运行时改优先方法 A |
| krkr2/krkrz | 自定义存档（TJS 数据结构序列化） | 借 TJS 引擎读改最稳（方法 A）；离线解析成本高 |

> **通用结论**：JSON 形态存档（MV/MZ、Tyrano）适合离线改；Marshal/pickle/自定义二进制存档
> （RGSS、Ren'Py、krkr）**优先运行时改**，离线改是兜底。

## 4. 操作骨架（Wolf 为例）

```powershell
# ① 判版本: 读 Game.exe PE 版本资源 → "WOLF RPG Editor 2.x/3.x"
# ② 备份: Save/ 整目录 → 备份区(含 Game.dat 一并备份)
# ③ 解析 Game.dat → 变量表(数值变量/字符串变量分开; Shift_JIS→UTF-8)
# ④ 定位目标变量(id + 名称) → 改值/改定义
# ⑤ 写回 → 校验(格式魔数 + 长度/节表一致)
# ⑥ 实机验证: 游戏读档,面板/行为确认
# ⑦ 卸载工具时: 清掉工具专用存档目录(原版兼容)
```

## 5. 坑位表

| 坑 | 现象 | 正解 |
|---|---|---|
| 按字节扫描数据文件猜结构 | 偏移不稳定、版本一变全错 | **按引擎格式规范解析**（类型标签/节表），版本分桶 |
| 忽略 Shift_JIS/码页 | 中文乱码、字符串长度错位 | 带码页转换层；Wolf 有专用码页开关 |
| 改了字符串没改长度字段 | 后续数据全错位 | 同步更新长度/指针字段；首选"等长替换"或完整重写 |
| 工具写回的存档原版读不了 | 原版 exe 启动异常 | 工具存档隔离目录 + 卸载时清理；同步格式版本号 |
| MV/MZ 加密包里直改 JSON | 改不到（包是压缩/加密的） | 走 VFS/解包后改，或运行时 eval 改内存 DB |
| RGSS 存档用别的语言解析 | Marshal 版本不兼容直接报错 | 用对应 Ruby 版本解析；或改走运行时 eval |
| 只备份存档不备份数据库 | 改库失败无法回滚 | Game.dat/rxdata 与存档**一起**备份 |

## 6. 与其它方法的关系

- **B ↔ C**：Wolf 的"变量表"本质是把文件数据库映射成 C 方法的对象表；MV/MZ 的数据编辑器改的是
  同一个对象模型的**文件侧**。
- **B → A**：改完数据库后，运行时值仍可用方法 A 即时改（两者叠加覆盖"定义+当前值"）。
- **B 与 E**：互不替代——E 改内存易失，B 改文件持久；RM2k 存档格式封闭时 E 是主力。
